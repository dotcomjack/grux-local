# The 2B republished with num_batch 256 (2026-11-27)

What this shows: on November 27, 2026, `gruxai.com/grux/grux-local:2b` moved from manifest `sha256:1622ac1b...` to
`sha256:86255f201bd61aef2d4b4d43b00de50f6f491195f55e474e041253bdd9818a99`, the same build with one parameter added,
`num_batch 256`. Why the parameter, what it changed in every set we score, and the one place it scores below the build
it replaced, which the house rule forbids and DotcomJack waived.

## Why num_batch

Ollama 0.40.8 runs this GGUF on llama.cpp's `llama-server`, with `-b` and `-ub` set to the model's num_batch, 1,024
by default. For Qwen 3.5, a hybrid model (linear attention beside full attention), the server's log shows it reusing
a prompt it has seen by restoring a saved context checkpoint and evaluating the rest of the prompt again, and the
checkpoint it restores sits one ubatch before the end of the last prompt (below: 4,359 of 5,383 tokens at 1,024, and
5,127 at 256). So every Grux turn, whose long system prompt is the same from one turn to the next, evaluated about
num_batch tokens again before its first word.

Grux 3.3.1 does not set num_batch. A local turn's options are num_ctx, num_predict and temperature
([`Grux-Mac/Sources/Grux/Backend/OpenAICompatBackend.swift:293-296`](https://github.com/dotcomjack/grux/blob/v3.3.1/Grux-Mac/Sources/Grux/Backend/OpenAICompatBackend.swift#L293-L296)
at v3.3.1, and no Swift file at that tag names num_batch), so the value in the model's params layer is the one a Grux
user runs.

[`probe/batch_test.sh`](../mini-nb256-20261127/probe/batch_test.sh) started a second Ollama on the Mac mini (port
11501, the same store) and ran [`probe/batch_probe.py`](../mini-nb256-20261127/probe/batch_probe.py) on 1622ac1b at
num_batch 1,024, 512, 256, 128 and 64: per value, one request with a ~5,400-token system prompt, then three that share
it and differ in the user turn. The server log's lines that name the batch, a restored checkpoint, a prompt's
evaluation or a request are in [`probe/batch-extract.log`](../mini-nb256-20261127/probe/batch-extract.log) (made with
the `grep` that [`sources.py`](../mini-nb256-20261127/sources.py) names, from a log whose sha256 was
`a599feba0c26d3817e6a716dd7036fbf7f2ffa652a69bc63a98b81c76d957c63`). Part 1 below reads them: each repeat evaluated one
token more than num_batch (the third six fewer, its user turn being shorter), at 1.1 ms a token at 1,024 and 1.2 ms
at 256, while the cold request took 5,711 ms at 256 against 5,550 ms at 1,024.

## The waiver

The house rule, in [`recipe/README.md`](../../recipe/README.md#3-replace-a-tag-only-with-a-version-that-is-not-worse),
is that a new Grux Local never replaces a tag it scores below. `results/gate.py`, which checks held-out v1, passes this
build against 1622ac1b:

```
$ python3 results/gate.py results/mini-nb256-20261127/runs/nb256/grux-local-2b-r5-nb256-holdout.jsonl --tag 2b
SHIP 2b: candidate 439/464, injection 64, against shipped 439/464, injection 64
```

On the local turns at num_ctx 8,192 it scores one task below 1622ac1b, 196 against 197 (lost h2-injection-014,
h2-injection-016 and h2-injection-057; gained h2-chat_tools-041 and h2-chat_tools-081), so the rule forbids the
replacement there. DotcomJack waived the rule for this build on November 27, 2026, for the sooner first word on the
local turns: a median of 0.32 s against 1.09 s at num_ctx 8,192.
